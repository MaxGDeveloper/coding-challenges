# Практика: командный сайт на Vue 3 + Git + GitHub Actions + GitHub Pages

**Формат:** групповая работа. Вся группа работает в одном репозитории и делает один сайт.
**Стек:** Vue 3 (Composition API, `<script setup>`), Vite, TypeScript, Vue Router.
**Цель:** освоить Git-ветки, pull request, review и CI/CD на GitHub. Сайт — полигон.

> Весь код — компоненты, страницы, роутер, конфиг Vite и workflow-файлы — вы пишете сами. В задании есть только требования к результату и критерии приёмки.

> В примерах используется ветка `main`. Если ваша основная ветка — `master`, замените `main` на `master` везде, включая workflow-файлы.

---

## 1. Что должно получиться

Публичный сайт на GitHub Pages с двумя типами страниц:

1. **Главная `/`** — сетка карточек разработчиков. Карточка ведёт на личную страницу автора.
2. **Личная страница `/#/developers/<slug>`** — расширенная информация о студенте. Оформление свободное.

Ключевое условие: **карточка — один общий компонент** `DeveloperCard`. Техлид пишет его один раз, студенты его **не меняют**, а только передают свои данные. Формат карточек одинаковый, личные страницы — разные.

```
Главная / [карточка 1] [карточка 2] [карточка 3] ...
                |            |            |
                v            v            v
     /#/developers/ivan  /#/developers/anna  /#/developers/oleg
```

## 2. Роли

| Роль | Кто | Что делает |
|---|---|---|
| **Техлид** | один студент | Создаёт репозиторий и каркас, общий компонент, главную, пример личной страницы и маршрута; настраивает CI/CD, Pages и защиту `main`; приглашает группу и проводит демо. Свою карточку и страницу добавляет так же, как все. |
| **Студент** | каждый участник | Делает ветку, добавляет карточку и личную страницу с маршрутом, открывает PR, проходит CI, мержит, проверяет деплой. |
| **Преподаватель** | — | Принимает работу и проверяет понимание механизма по вопросам из раздела 9. |

## 3. Этап 1. Техлид: репозиторий и инфраструктура

### 3.1. Репозиторий и каркас

1. Создайте **пустой публичный** репозиторий — без README, `.gitignore` и лицензии, иначе первый push конфликтует с автокоммитом GitHub. Добавьте группу в Collaborators с правом Write.
2. Создайте проект через `npm create vue@latest` (scaffold в текущую папку), включив TypeScript и Vue Router. Установите зависимости.
3. Сделайте первый commit и push в `main`.
4. Убедитесь, что `package-lock.json` закоммичен — без него `npm ci` в CI не сможет установить зависимости.

### 3.2. Общий компонент карточки `DeveloperCard`

Требования к компоненту:

- Это **единственный** компонент карточки в проекте. Студенты его не редактируют.
- Принимает пропсы: `name` (string, обязателен), `role` (string, обязателен), `shortDescription` (string, обязателен), `avatar` (string, необязателен), `to` (маршрут личной страницы, обязателен).
- Отображает аватар, если он передан; если нет — инициалы (первая буква имени).
- Отображает имя, роль, краткое описание и призыв «Подробнее».
- Вся карточка целиком — ссылка-переход на личную страницу (`RouterLink` или эквивалент). Внутри **не должно** быть вложенных ссылок и кнопок.
- Стили изолированы (`scoped`), карточка корректно выглядит в сетке при разной длине текста.

### 3.3. Главная страница

- Сетка карточек: адаптивная, автоматически заполняет строку, разумные отступы и максимальная ширина контейнера.
- Заголовок страницы.
- Одна карточка-пример: заполнена данными техлида и ведёт на страницу-пример.
- Каждый студент позже добавит сюда **одну** свою карточку в конец списка.

### 3.4. Пример личной страницы и роутер

- Создайте страницу-пример для техлида. На ней минимум три блока: «Обо мне», «Навыки и проекты», «Контакты / увлечения». Это образец для студентов.
- Роутер: два маршрута — главная (`/`) и страница-пример (`/developers/example`). Ленивая загрузка страницы разработчика приветствуется.
- **Роутер должен работать в hash-режиме** (`/#/developers/ivan`), а не в history-режиме. Причина: GitHub Pages — статический хостинг, при прямом заходе на `/developers/ivan` он ищет файл и отдаёт 404. Hash-режим работает без серверных настроек.
- Роутер подключён в точке входа приложения; корневой компонент отображает только `<RouterView />`.
- Удалите демо-компоненты шаблона (`HelloWorld` и подобные) — иначе они останутся на всех страницах.
- В глобальных стилях оставьте только базовые правила (шрифт, фон, `box-sizing`). Демо-стили шаблона (ограничение ширины `#app`, `display: flex` и т. п.) ломают сетку карточек — их нужно убрать.

### 3.5. База для GitHub Pages

В конфиге Vite должен вычисляться корректный `base`:

| Имя репозитория | URL сайта | `base` |
|---|---|---|
| `<user>.github.io` | `https://<user>.github.io/` | `/` |
| `<team>-site` | `https://<user>.github.io/<team>-site/` | `/<team>-site>/` |

Требование: `base` определяется автоматически из имени репозитория (переменная окружения `GITHUB_REPOSITORY` доступна в CI), с fallback на `/` для репозитория вида `<user>.github.io` и для локального запуска. Если `base` неверный — сайт откроется пустым, потому что JS и CSS будут грузиться по неправильному пути.

### 3.6. CI: проверка pull request

Настройте workflow, который:

- запускается **на pull request в `main`** (открытие, обновление, повторное открытие);
- имеет минимальные права: только чтение содержимого репозитория;
- на Node.js 22 с кешированием npm выполняет `npm ci` и затем `npm run build`;
- назовите job `build` — этот чек вы later добавите в обязательные проверки ветки.

CI не публикует сайт. Его задача — не пустить в `main` код, который не собирается.

### 3.7. CD: публикация сайта

Настройте workflow, который:

- запускается **на push в `main`** и дополнительно может запускаться вручную (`workflow_dispatch`);
- имеет права `contents: read`, `pages: write`, `id-token: write` — без двух последних публикация невозможна;
- использует группу concurrency для Pages, чтобы деплои не накладывались друг на друга;
- в job сборки: `npm ci`, `npm run build`, настройка Pages, загрузка артефакта из папки `dist`;
- в отдельном job деплоя (зависит от сборки): публикация артефакта в окружение `github-pages` и вывод URL сайта.

PR-код на сайт не попадает: деплой срабатывает только после merge в `main`.

### 3.8. Включение Pages и защиты `main`

1. Закоммитьте оба workflow-файла в `main`. Без этого GitHub их не увидит, и пункт **Run workflow** не появится.
2. Settings → Pages → Build and deployment → **Source: GitHub Actions**.
3. Дождитесь зелёного деплоя и откройте URL сайта.
4. **После первого успешного деплоя** защитите `main`:
   - require a pull request before merging;
   - require 1 approval;
   - require status checks: `build` (в списке может отображаться как `CI / build`);
   - require branches to be up to date;
   - запрет force push и удаления ветки.

   *Если чек `build` ещё не появлялся в списке доступных — откройте тренировочный PR из ветки `chore/test-ci`, дайте CI отработать, добавьте `build` в обязательные проверки и закройте PR.*

Защита включается после первого push: иначе техлид не сможет залить исходный каркас. После включения прямой push в `main` должен быть невозможен.

### 3.9. README и демо

В README укажите: URL сайта, как запустить локально, правило веток и PR, кто техлид.

Проведите короткое демо группе (10–15 минут): карточка → страница → PR → зелёный CI → merge → обновление сайта. После демо студенты начинают свои ветки.

## 4. Этап 2. Каждый студент: добавить себя

### Шаг 1. Подготовка

Склонируйте репозиторий, установите зависимости через `npm ci`, запустите dev-сервер. Убедитесь, что главная и страница-пример открываются.

### Шаг 2. Своя ветка

Обновите `main` и создайте ветку `feature/<фамилия-имя>` (например, `feature/ivan-petrov`). Работать в `main` напрямую нельзя — он защищён.

### Шаг 3. Карточка на главной

Добавьте **в конец** списка карточек на главной свою, передав общему компоненту: имя, роль, краткое описание (1–2 предложения) и маршрут личной страницы. Имя маршрута в `:to` — ваш slug.

Если есть фото — положите его в `src/assets/`, импортируйте на главной и передайте в карточку. Если фото нет — компонент покажет инициалы, ничего дополнительно делать не нужно.

Компонент карточки **не редактируйте**: если считаете, что в нём есть баг или недоработка — напишите техлиду, а не правьте его в своей ветке.

### Шаг 4. Личная страница

Создайте отдельный файл-компонент личной страницы. Оформление свободное, но обязательно должны быть блоки:

- имя и краткая шапка;
- «Обо мне»;
- «Навыки и проекты»;
- «Контакты / увлечения».

Не копируйте чужие страницы и не используйте чужие фото.

### Шаг 5. Маршрут

Добавьте маршрут **в конец** массива маршрутов: путь `/developers/<slug>`, имя маршрута `<slug>` (должно совпадать с `:to` у карточки), компонент — ваша страница.

### Шаг 6. Проверка и коммит

Локально выполните `npm run build` — сборка должна проходить без ошибок TypeScript. Сделайте 2–3 осмысленных коммита. Не коммитьте `node_modules`, `dist`, `.env`.

### Шаг 7. Pull request

Откройте PR из своей ветки в `main`. В описании укажите:

- что добавлено;
- ожидаемый URL страницы (например, `https://<user>.github.io/<repo>/#/developers/ivan-petrov`);
- скриншот главной с вашей карточкой и скриншот личной страницы;
- чек-лист: сборка проходит, чужие карточки и маршруты не удалены.

### Шаг 8. CI

Дождитесь проверки. Если CI красный: откройте Actions → упавший run → job `build` → шаг с ошибкой, прочитайте ошибку, исправьте локально, сделайте commit и push, добейтесь зелёного CI.

Пока CI красный — merge заблокирован, это нормально.

### Шаг 9. Конфликты

Так как все редактируют главную и файл роутера, конфликты **ожидаемы**. Это часть задания.

Получите свежий `main` и перебазируйте свою ветку на него. Откройте конфликтные файлы: на главной оставьте **все** карточки, включая чужие; в роутере — **все** маршруты. Уберите маркеры конфликта, отметьте файлы как разрешённые, продолжите rebase и запушьте ветку с `--force-with-lease` (только в свою ветку; в `main` force push запрещён).

Если при продолжении rebase откроется редактор с сообщением коммита — сохраните и закройте его.

Не удаляйте чужую карточку или маршрут, чтобы «быстрее смержить».

### Шаг 10. Merge и проверка деплоя

После approval (его ставит техлид или другой студент; свой PR approve нельзя) и зелёного CI:

1. Нажмите **Squash and merge**.
2. Удалите ветку.
3. Дождитесь зелёного **Deploy to GitHub Pages**.
4. Откройте сайт и проверьте свою карточку и страницу.

## 5. Как это работает

| Действие | Что запускается | Результат |
|---|---|---|
| Push в `feature/...` | Ничего автоматически | Ветка появилась на GitHub |
| Открытие/обновление PR в `main` | CI: `npm ci`, `npm run build` | Красный CI блокирует merge |
| Merge PR в `main` | CD: build, artifact, deploy | Сайт обновляется на GitHub Pages |
| Ошибка деплоя | — | Сайт остаётся на предыдущей версии |

Правило: изменение попадает на сайт только так —

```
ветка студента → PR → review → зелёный CI → merge в main → deploy → GitHub Pages
```

Именно эту цепочку нужно уметь объяснить на тесте.

## 6. Правила Git

- Один студент — одна ветка — один PR.
- Ветка: `feature/<фамилия-имя>`.
- Коммиты осмысленные: `feat: add Ivan Petrov card`, `feat: add Ivan Petrov page`, `fix: resolve route conflict`.
- PR только в `main`, после зелёного CI и approval.
- Merge — **Squash and merge**, ветку удалить.
- При конфликте сохранять все карточки и маршруты.
- Не коммитить `node_modules`, `dist`, `.env`, секреты и большие файлы.
- Никакого force push в `main`. `--force-with-lease` — только в своей ветке после rebase.

## 8. Критерии приёмки

- [ ] Сайт открывается по публичному URL.
- [ ] На главной видны карточки всех студентов.
- [ ] Каждая карточка ведёт на личную страницу автора.
- [ ] На личной странице есть расширенная информация (3+ блока).
- [ ] Карточки — один общий компонент, студенты его не переписывали.
- [ ] `main` защищён: прямой push невозможен.
- [ ] Все изменения прошли через PR и review.
- [ ] CI на PR зелёный, deploy на `main` зелёный.
- [ ] Сайт обновился после merge.
- [ ] В репозитории нет секретов, `node_modules` и `dist`.
- [ ] Студент может объяснить путь своего изменения до сайта.

## 9. Вопросы для проверки понимания

По этим вопросам будет тест. Ответы — своими словами, с опорой на свой PR и workflow.

1. Что происходит при push в вашу ветку? Запускается ли деплой?
2. Какие workflow запускаются на PR, а какие — при merge в `main`?
3. Почему прямой push в `main` запрещён? Что включает branch protection?
4. Почему сайт обновляется только после merge, а не после push в ветку?
5. Зачем в CI нужен `npm ci`, а не `npm install`?
6. Что делают `actions/configure-pages`, `upload-pages-artifact` и `deploy-pages`?
7. Зачем нужны `permissions: pages: write` и `id-token: write`?
8. Почему возник конфликт в главной странице или файле роутера? Как вы его разрешили, не удалив чужой вклад?
9. Почему выбран hash-режим роутера? Что будет при history-режиме на GitHub Pages?
10. Как проверить, что на сайте именно ваша версия страницы?

## 11. Если что-то пошло не так

| Проблема | Что проверить |
|---|---|
| Сайт 404 | Settings → Pages → Source: GitHub Actions; последний deploy run; корректность `base` в конфиге Vite |
| Пустая страница | DevTools → Network: не 404 ли JS/CSS; правильный ли `base` |
| Прямая ссылка на страницу 404 | Используется ли hash-режим роутера |
| CI красный | Actions → run → job `build` → шаг с ошибкой; запустить `npm run build` локально |
| Нельзя запушить в `main` | Это branch protection. Создайте ветку и PR |
| PR конфликтует | Обновите `main`, перебазируйте ветку, сохраните все карточки и маршруты |
| Деплой красный | Лог deploy-workflow: права (`pages: write`, `id-token: write`), источник Pages, наличие папки `dist` |
| CI не запускается на PR | Workflow есть в `main`; в триггере указана ваша основная ветка |
| Картинка не грузится | Импортируйте файл в компонент; для файлов из `public/` стройте путь через `import.meta.env.BASE_URL` |
