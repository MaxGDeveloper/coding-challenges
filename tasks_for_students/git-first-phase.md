# Практика Git и GitHub

Студентам предполагается самостоятельно искать синтаксис команд в документации (`git help <command>`, официальный Git Book, GitHub Docs).

---

## Общие требования

- Все действия выполняются в консоли (кроме явно указанных шагов в GitExtension и на GitHub).
- Для сдачи практики нужны скриншоты, отмеченные в задании как **(скриншот)**.
- Сообщения коммитов должны быть осмысленными и отражать суть изменения.
- Если команда или её опции незнакомы — ищите в документации.

## Тема 1. `git init`, `git status`, первый коммит

1. Настройте `user.name` и `user.email` (глобально или локально для репозитория).
2. Создайте папку `git-day1`, внутри — файл `hello.txt` с произвольной строкой.
3. Инициализируйте репозиторий, добавьте файл в индекс и сделайте коммит с осмысленным сообщением.
4. Измените `hello.txt`, снова добавьте и закоммитьте.
5. Выведите `git log --oneline` и сохраните **(скриншот)**.

---

## Тема 2. `git diff`, `git restore`, `git reset`, `.gitignore`

6. В репозитории `git-day1` создайте файлы `secret.txt` и `app.log`.
7. Добавьте в `.gitignore` строки:
   ```
   *.log
   secret.txt
   ```
8. Убедитесь через `git status`, что эти файлы не отображаются как неотслеживаемые.
9. Измените `hello.txt`, посмотрите `git diff`, затем отмените изменение через `git restore`.
10. Сделайте коммит, затем отмените его через `git reset --soft HEAD~1` и снова закоммитьте.
11. Продемонстрируйте `git diff --staged` перед коммитом **(скриншот)**.

## Тема 3. Ветки, merge, fast-forward vs трёхсторонний merge

12. В `git-day1` создайте ветку `feature-a` и переключитесь на неё.
13. Добавьте в `hello.txt` строку `Строка из feature-a`, закоммитьте.
14. Переключитесь на `main`, добавьте строку `Строка из main`, закоммитьте.
15. Выполните `git merge feature-a` из `main`.
16. Разрешите конфликт вручную: оставьте обе строки (либо одну — по указанию преподавателя).
17. Завершите merge, посмотрите `git log --graph --oneline --all`.
18. Создайте вторую ветку `feature-b`, сделайте в ней коммит, переключитесь на `main`, выполните `git merge feature-b` и зафиксируйте, что произошёл fast-forward (при условии, что `main` не двигался).

## Тема 4. Связь локального и удалённого репозитория: `origin`, tracking branch, `fetch` vs `pull`

19. Создайте пустой репозиторий на GitHub.
20. Свяжите локальный `git-day1` с удалённым: `git remote add origin ...`.
21. Выполните `git push -u origin main`.
22. На стороне GitHub через веб-интерфейс добавьте файл `README.md` с произвольной строкой и закоммитьте в `main`.
23. Локально выполните `git fetch origin`, затем `git log --oneline main..origin/main` — увидите расхождение.
24. Выполните `git pull origin main`, убедитесь, что `README.md` появился локально.
25. Сделайте локальное изменение, закоммитьте, отправьте `git push`.

---

## Тема 5. Rebase, cherry-pick, stash

26. Создайте ветку `feature-rebase` от `main`, сделайте в ней 2 коммита.
27. В `main` сделайте ещё один коммит.
28. Переключитесь на `feature-rebase` и выполните `git rebase main`.
29. Убедитесь, что `git log --graph --oneline --all` показывает линейную историю `feature-rebase` поверх `main`.
30. Найдите хеш одного из коммитов в `feature-rebase`, переключитесь на `main` и выполните `git cherry-pick <hash>`.
31. Незакоммиченное изменение в `main` спрячьте через `git stash`, переключитесь на другую ветку, вернитесь, восстановите через `git stash pop`.

## Тема 6. Разбор аварийных сценариев

### Сценарий A. Detached HEAD

32. Студент случайно сделал `git checkout <старый-хеш>` и оказался в detached HEAD. Через `git reflog` найдите последний коммит ветки `main` и вернитесь: `git switch main` или `git checkout -B main <хеш>`.

### Сценарий B. Секретный файл попал в коммит

33. Удалите его из последнего коммита:
    - `git rm --cached secret.txt`
    - добавьте `secret.txt` в `.gitignore`
    - `git commit --amend`

### Сценарий C. Коммит не в ту ветку

34. Коммит сделан в `main` вместо `feature-x`. Перенесите коммит:
    - `git branch feature-x`
    - `git reset --hard HEAD~1`
    - `git switch feature-x`

### Вопрос

35. Письменно ответьте: почему `git push --force` опасен в командной работе и чем `--force-with-lease` лучше.

## Тема 7. GitExtension: базовые операции

36. Откройте в GitExtension репозиторий `git-day1` через **Open repository**.
37. Измените `hello.txt`, выделите файл в списке изменений, введите сообщение коммита и нажмите **Commit**.
38. Нажмите **Push** и убедитесь, что коммит ушёл на GitHub.
39. Нажмите **Pull**, чтобы получить изменения, сделанные на GitHub через веб-интерфейс (если они есть).
40. Откройте **Browse** и найдите тот же коммит, который ранее был сделан через консоль.

---

## Тема 8. GitExtension: ветки, merge, конфликты, stash

41. В GitExtension создайте ветку `gui-feature` от `main`.
42. Переключитесь на неё, измените `hello.txt`, закоммитьте через GUI.
43. Переключитесь на `main`, измените ту же строку в `hello.txt`, закоммитьте.
44. Выполните merge `gui-feature` в `main` через контекстное меню.
45. Разрешите конфликт: откройте файл, уберите маркеры, сохраните, добавьте файл в индекс через GUI, завершите merge.
46. Сделайте незакоммиченное изменение и спрячьте его через **Stash**, затем восстановите через **Stash pop**.

## Тема 9. GitHub: Issues, Merge Request, ревью

47. В GitHub создайте Issue с описанием задачи: «Добавить в `hello.txt` строку с именем студента».
48. Создайте ветку `GitHub-task-1` от `main` на стороне GitHub или локально и запушьте.
49. Локально внесите изменение, закоммитьте, запушьте ветку `GitHub-task-1` в GitHub.
50. На GitHub создайте Merge Request из `GitHub-task-1` в `main`.
51. В описании MR укажите `Closes #<номер issue>` (или свяжите issue вручную).
52. Проведите самопроверку MR: посмотрите diff, убедитесь, что нет лишних файлов.
53. Смёржьте MR (можно с удалением исходной ветки).
54. Убедитесь, что Issue автоматически закрылся (если использовался `Closes`).

## Тема 10. Имитация командной работы: форк, MR из форка, ревью

55. Студенты работают в парах: каждый делает форк проекта.
56. Сделайте **Fork** проекта в свой аккаунт GitHub.
57. Клонируйте форк локально.
58. Создайте ветку `final-task`, добавьте файл `students/<имя>.md` с краткой информацией о себе, закоммитьте и запушьте в свой форк.
59. Создайте Merge Request из своей ветки в `main` исходного проекта (**upstream**).
60. В качестве ревьюера выступите для MR партнёра: оставьте минимум один содержательный комментарий (не «ок», а замечание или вопрос по diff).
61. Автор MR отвечает на комментарий и, если нужно, вносит правку и пушит — MR обновляется.
62. После одобрения (или по инструкции листка) смержьте MR.
63. Письменно ответьте: чем MR из форка отличается от MR из ветки внутри одного проекта; зачем нужен `upstream`.
