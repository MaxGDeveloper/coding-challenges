# Практика Git и GitHub

- **Формат:** индивидуальная практика в консоли и на GitHub.
- **Цель:** пройти все темы вводного теста на практике и сдать отчёт Word с доказательствами.

Работа выполняется в двух публичных репозиториях: `git-day1` для тем 1–9 и форк проекта
для темы 10.

## Документация

Синтаксис команд ищите самостоятельно — это часть задания.

- Pro Git на русском: <https://git-scm.com/book/ru/v2>
- Справочник команд: <https://git-scm.com/docs>
- GitHub Docs на русском: <https://docs.github.com/ru>
- Локальная справка: `git help <команда>` или `git <команда> -h`

## Общие требования

- Все действия выполняются в консоли, кроме шагов, где явно указаны GitExtension или
  веб-интерфейс GitHub.
- Скриншоты, отмеченные в задании как **(скриншот)**, обязательны и вставляются в отчёт.
- Сообщения коммитов должны быть осмысленными и отражать суть изменения.
- Если команда или её опции незнакомы — ищите в документации, а не копируйте наугад.
- В репозиториях не должно быть секретов, `node_modules`, `dist` и `.env`.

## Тема 1. Репозиторий, индекс и первый коммит

1. Настройте `user.name` и `user.email` — глобально или локально для репозитория.
2. Создайте папку `git-day1`, внутри — файл `hello.txt` с произвольной строкой.
3. Инициализируйте репозиторий с веткой `main`: `git init -b main`.
   В старых версиях Git: `git init`, затем `git branch -M main`.
4. Посмотрите `git status` — файл неотслеживаемый. Добавьте его в индекс через
   `git add hello.txt` и снова посмотрите `git status` — файл готов к коммиту.
5. Сделайте первый коммит с осмысленным сообщением.
6. Измените `hello.txt`, посмотрите `git diff`, добавьте файл в индекс и выполните
   `git diff --staged` **(скриншот)**. Сравните, что показывает каждая команда.
7. Закоммитьте изменение. Выполните `git log --oneline` и `git show HEAD`
   **(скриншот)** — убедитесь, что `show` показывает содержимое последнего коммита.

## Тема 2. Игнорирование файлов, `restore` и `reset`

8. В репозитории `git-day1` создайте файлы `secret.txt` и `app.log`.
9. Добавьте в `.gitignore` строки:

   ```
   *.log
   secret.txt
   ```

10. Убедитесь через `git status`, что файлы не отображаются как неотслеживаемые.
    Затем выполните `git status --ignored` **(скриншот)** — Git покажет, что файлы
    игнорируются.
11. Измените `hello.txt`, посмотрите `git diff`, затем верните файл к версии из индекса
    через `git restore hello.txt`. Убедитесь, что `git diff` снова пуст.
12. Добавьте изменение в индекс, затем измените файл ещё раз. Сравните `git diff`
    (правка после индексации) и `git diff --staged` (версия, уже лежащая в индексе).
    Уберите файл из индекса через `git restore --staged hello.txt`.
13. Сделайте коммит, отмените его через `git reset --soft HEAD~1`, посмотрите
    `git status` (изменения остались в индексе) и закоммитьте снова. Если индекс пуст,
    `git commit` не создаст коммит.
14. Запомните: `git reset --hard` удаляет незакоммиченные изменения без возможности
    вернуть их обычным способом. Он применяется осознанно — это разбирается в теме 6.

## Тема 3. Ветки, merge, fast-forward, конфликты

15. Создайте ветку `feature-a` и сразу переключитесь на неё: `git switch -c feature-a`.
16. Добавьте в `hello.txt` строку `Строка из feature-a` и закоммитьте.
17. Переключитесь на `main`, добавьте в то же место строку `Строка из main`
    и закоммитьте.
18. Выполните `git merge feature-a` из `main`. Возникнет конфликт. Посмотрите
    `git status` и маркеры конфликта в файле.
19. Отмените слияние через `git merge --abort` **(скриншот)**. Убедитесь, что
    `git status` показывает чистый рабочий каталог, а `hello.txt` вернулся к версии
    до merge.
20. Повторите `git merge feature-a`, разрешите конфликт вручную (оставьте обе строки),
    добавьте файл в индекс через `git add hello.txt` и завершите merge командой
    `git commit` без `-m` — Git подставит стандартное сообщение merge-коммита.
21. Выполните `git log --graph --oneline --all` **(скриншот)**. Убедитесь, что
    появился merge-коммит с двумя родителями.
22. Создайте ветку `feature-b`, сделайте в ней коммит, переключитесь на `main`
    и выполните `git merge feature-b`. Так как `main` не двигался, произойдёт
    fast-forward: merge-коммита не будет, `main` просто перейдёт на коммит `feature-b`.
23. Удалите слитые ветки: `git branch -d feature-b` и `git branch -d feature-a`.
    Проверьте `git branch`, что осталась только `main`. Если ветка не слита,
    `-d` откажется её удалять — принудительное удаление `-D` применяется осознанно.

## Тема 4. Удалённый репозиторий, tracking, `fetch` и `pull`

24. Создайте на GitHub пустой публичный репозиторий без README и лицензии.
25. Свяжите локальный `git-day1` с удалённым: `git remote add origin <url>`.
    Проверьте `git remote -v`.
26. Отправьте ветку и настройте upstream: `git push -u origin main`.
27. Выполните `git branch -vv` **(скриншот)** — у `main` должен появиться upstream
    `origin/main`.
28. На стороне GitHub через веб-интерфейс добавьте файл `README.md` с произвольной
    строкой и закоммитьте его в `main`.
29. Локально выполните `git fetch origin`. Обратите внимание: рабочая копия не
    изменилась, но `origin/main` обновился. Посмотрите расхождение через
    `git log --oneline main..origin/main` **(скриншот)**.
30. Выполните `git pull origin main` и убедитесь, что `README.md` появился локально.
    Сделайте локальное изменение, закоммитьте и отправьте через `git push`.

## Тема 5. Rebase, `cherry-pick`, stash

31. Создайте ветку `feature-rebase` от `main` и сделайте в ней 2 коммита.
32. В `main` сделайте ещё один коммит.
33. Переключитесь на `feature-rebase` и выполните `git rebase main`.
34. Убедитесь через `git log --graph --oneline --all` **(скриншот)**, что история
    `feature-rebase` стала линейной поверх `main`.
35. Найдите хеш одного из коммитов `feature-rebase` через `git log --oneline`,
    переключитесь на `main` и выполните `git cherry-pick <hash>`. Посмотрите
    `git log --oneline -3` **(скриншот)**: появился новый коммит с теми же изменениями,
    но с другим хешем. В отчёте объясните, чем это отличается от merge.
36. Сделайте незакоммиченное изменение в `main`, спрячьте его через `git stash`,
    переключитесь на другую ветку, вернитесь и восстановите изменение через
    `git stash pop`. Проверьте `git stash list`.

## Тема 6. Аварийные сценарии и откаты

### Сценарий A. Detached HEAD

37. Сделайте `git checkout <старый-хеш>` и окажитесь в detached HEAD. Через
    `git reflog` найдите последний коммит ветки `main` **(скриншот)** и вернитесь:
    `git switch main` или `git checkout -B main <хеш>`.

### Сценарий B. Секретный файл попал в коммит

38. Создайте `config.env`, закоммитьте его, затем уберите из отслеживания:
    - `git rm --cached config.env` — файл останется на диске;
    - добавьте `config.env` в `.gitignore`;
    - закоммитьте удаление файла из индекса обычным коммитом.

    Убедитесь, что `git status` чист. В отчёте объясните: файл исчез из текущей версии
    репозитория, но остался в истории. Если в файле был настоящий секрет, его нужно
    перевыпустить, а историю — переписать отдельно и согласованно со всей командой.

### Сценарий C. Коммит не в ту ветку

39. Сделайте коммит в `main`, хотя он должен быть в `feature-x`. Убедитесь, что
    `git status` чист (незакоммиченных изменений нет), затем:
    - `git branch feature-x` — сохранит коммит в новой ветке;
    - `git reset --hard HEAD~1` — уберёт коммит из `main`;
    - `git switch feature-x` — проверьте, что коммит остался там.

    `--hard` здесь безопасен только потому, что рабочая копия чистая. В отчёте
    объясните, что произошло бы с незакоммиченными изменениями.

### Сценарий D. Откат опубликованного коммита

40. В `main` сделайте коммит с намеренно ошибочным изменением и отправьте его на GitHub.
    Отмените его через `git revert <hash>` — Git создаст новый коммит с обратными
    изменениями. Отправьте результат через `git push` и посмотрите
    `git log --oneline` **(скриншот)**. Убедитесь, что старый коммит остался в истории.
    В отчёте объясните, почему для общей ветки используют `revert`, а не `reset`.

## Тема 7. GitExtension: базовые операции

41. Откройте в GitExtension репозиторий `git-day1` через **Open repository**.
42. Измените `hello.txt`, выделите файл в списке изменений, введите сообщение коммита
    и нажмите **Commit**.
43. Нажмите **Push** и убедитесь, что коммит ушёл на GitHub.
44. Нажмите **Pull**, чтобы получить изменения, сделанные на GitHub через веб-интерфейс.
45. Откройте **Browse** и найдите тот же коммит, который ранее был сделан через консоль.

## Тема 8. GitExtension: ветки, merge, конфликты, stash

46. В GitExtension создайте ветку `gui-feature` от `main`.
47. Переключитесь на неё, измените `hello.txt`, закоммитьте через GUI.
48. Переключитесь на `main`, измените ту же строку в `hello.txt`, закоммитьте.
49. Выполните merge `gui-feature` в `main` через контекстное меню.
50. Разрешите конфликт: откройте файл, уберите маркеры, сохраните, добавьте файл
    в индекс через GUI и завершите merge.
51. Сделайте незакоммиченное изменение и спрячьте его через **Stash**, затем
    восстановите через **Stash pop**.

## Тема 9. GitHub: Issue, Pull Request, review, CI

> На GitHub используется термин **Pull Request (PR)**. **Merge Request (MR)** — это
> термин GitLab; не ищите кнопку MR в интерфейсе GitHub.

52. В GitHub создайте Issue с описанием задачи: «Добавить в `hello.txt` строку
    с именем студента».
53. Создайте ветку `GitHub-task-1` от `main` на стороне GitHub или локально
    и запушьте её.
54. Локально внесите изменение, закоммитьте и запушьте ветку `GitHub-task-1`.
55. На GitHub создайте Pull Request из `GitHub-task-1` в `main` **(скриншот)**.
56. В описании PR укажите `Closes #<номер issue>`.
57. Проведите самопроверку PR: откройте **Files changed**, убедитесь, что в diff нет
    лишних файлов, секретов и случайных изменений. В отчёте объясните, что даёт PR
    кроме merge: review, обсуждение и прогон CI до попадания в общую ветку.
58. Откройте вкладку **Checks**. Если в репозитории настроен CI, дождитесь зелёной
    проверки. Если CI нет, зафиксируйте в отчёте, что проверок нет, и объясните,
    зачем CI нужен до merge. При желании добавьте минимальный workflow
    `.github/workflows/ci.yml`, который запускается на `pull_request`, и убедитесь,
    что проверка появилась в PR.
59. Смержьте PR (можно с удалением исходной ветки). Попробуйте **Squash and merge**
    и объясните в отчёте, чем он отличается от обычного merge. Убедитесь, что Issue
    автоматически закрылся. Локально переключитесь на `main` и выполните `git pull`.

## Тема 10. Форк, PR из форка, ревью

60. Работайте в паре: каждый делает форк одного и того же учебного проекта
    преподавателя.
61. Сделайте **Fork** этого проекта в свой аккаунт GitHub.
62. Склонируйте форк локально.
63. Проверьте `git remote -v` **(скриншот)**: `origin` указывает на ваш форк.
    `git branch -vv` покажет, что `main` уже связана с `origin/main`. Добавьте
    исходный проект как `upstream`:
    `git remote add upstream <url-исходного-проекта>` и снова посмотрите `git remote -v`.
64. Выполните `git fetch upstream`, создайте ветку `final-task` от `upstream/main`,
    добавьте файл `students/<имя>.md` с краткой информацией о себе, закоммитьте
    и запушьте ветку в свой форк: `git push -u origin final-task`.
65. Создайте Pull Request из своей ветки в `main` исходного проекта (**upstream**).
66. В качестве ревьюера выступите для PR партнёра: оставьте минимум один содержательный
    комментарий (не «ок», а замечание или вопрос по diff) **(скриншот)**.
67. Автор PR отвечает на комментарий и, если нужно, вносит правку и пушит в ту же
    ветку — PR обновляется автоматически.
68. После одобрения смержьте PR (или дождитесь, пока это сделает владелец
    `upstream`) и убедитесь, что изменения попали в `main` исходного проекта.

## Контрольные вопросы

Ответьте письменно в отчёте, полными предложениями. Ответы должны опираться на то,
что вы сделали руками, а не на заученные формулировки.

1. Чем `git fetch` отличается от `git pull`? Что происходит с рабочей копией после
   `fetch`?
2. Чем fast-forward merge отличается от merge-коммита? Что происходит с веткой после
   merge и как её удалить?
3. Зачем нужен `git merge --abort` и в какой момент его используют?
4. Чем `git revert` отличается от `git reset`? Почему для опубликованного коммита
   выбирают `revert`?
5. Чем отличаются `git reset --soft`, `git reset` и `git reset --hard`? В каком случае
   можно потерять изменения?
6. Что делает `git restore <файл>` и чем он отличается от `git restore --staged <файл>`?
7. Что делает `git cherry-pick`? Почему у нового коммита другой хеш и чем это
   отличается от merge?
8. Что такое tracking branch? Как он настраивается через `git push -u` и при
   `git clone`? Как посмотреть его через `git branch -vv`?
9. Почему `git push --force` опасен в командной работе и чем `--force-with-lease` лучше?
10. Чем PR из форка отличается от PR из ветки внутри одного проекта? Зачем нужен
    `upstream`?

## Отчёт

Сдаётся **один файл Word** (`.docx`), имя — `git-first-phase-<Фамилия>-<Имя>.docx`.
Скриншоты и ссылки должны быть внутри отчёта; отдельные файлы и папки со скриншотами
не принимаются.

### Структура отчёта

1. **Титульный лист:** ФИО, группа, дата.
2. **Ссылки:** на созданные репозитории, Issue и PR, PR партнёра, который вы
   ревьюили.
3. **Краткое описание:** что сделано, в каком репозитории, какие сложности возникли.
4. **Темы 1–10:** по каждой теме — что выполнено, ключевые команды, скриншоты
   с подписями, краткий вывод.
5. **Контрольные вопросы:** ответы на 10 вопросов выше.

### Что показать в отчёте по темам

| Тема | Доказательство |
|---|---|
| 1 | `git log --oneline`, `git show HEAD`, `git diff --staged` |
| 2 | `git status --ignored`, `git restore`, `git reset --soft` |
| 3 | конфликт и `git merge --abort`, merge-коммит и fast-forward, `git branch -d` |
| 4 | `git branch -vv`, `git log main..origin/main`, `fetch` и `pull` |
| 5 | линейный граф после rebase, новый коммит после `cherry-pick`, stash |
| 6 | `git reflog`, `git rm --cached`, `git reset --hard`, `git revert` в истории |
| 7–8 | скриншоты операций в GitExtension |
| 9 | Issue, PR, вкладка Checks, squash merge, смерженный PR |
| 10 | форк, `git remote -v` с `origin` и `upstream`, PR из форка, комментарий ревью |
